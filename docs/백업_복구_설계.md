# 데이터 백업·복구 설계 (정신과 EMR)

> 대상: 정신건강의학과 EMR 시스템의 **Postgres DB**(진료기록·척도검사·처방·입원·감사로그)
> 전제: **Supabase Cloud(관리형 PITR) + 국내 오프사이트 이중 보관**
> 법적 근거: 의료법 §22(진료기록 10년 보존)·§23(접근기록·위변조 방지), 개인정보보호법(안전성 확보조치)

---

## 1. 목적

- 진료기록의 **무손실·무위변조 보존**(의료법 §22 10년) 보장
- 사고(오삭제·오갱신·랜섬웨어·리전 장애·계정 상실)로부터 **신속 복구**
- 개인정보(암호화 이름·주민번호·진단)의 **국내 보관·암호화·접근통제** 준수

## 2. 설계 원칙

| 원칙 | 내용 |
|------|------|
| **3-2-1** | 사본 3벌 · 위치/공급자 2곳 · 오프사이트 1벌 → Supabase 운영본 + Supabase 관리백업 + **국내 오프사이트** |
| **불변성(WORM)** | 장기 아카이브는 Object Lock으로 보존기간 내 수정·삭제 불가 (물리삭제 금지 원칙과 일치) |
| **기본 암호화** | 저장 시 AES-256(봉투암호화), 전송 시 TLS 1.2+. 키는 백업과 분리 보관 |
| **검증된 백업만 백업** | 주기적 **복구 테스트**를 통과하지 않은 백업은 백업으로 인정하지 않음 |
| **국내 보관** | 오프사이트 사본과 그 처리(암호화·검증)는 **국내 인프라**에서 수행 |
| **최소권한** | 전용 백업 롤(읽기 전용) · 키 접근 분리 · 모든 접근 감사 |

## 3. 아키텍처 (3계층)

```
                         ┌─────────────────────────────────────┐
      운영 DB            │  Supabase Cloud (Postgres)           │
   (실시간 진료)         │   · WAL 연속 아카이브                 │
                         │   · Tier0: PITR (초 단위 복구)        │
                         └───────────────┬─────────────────────┘
                                         │ TLS, 읽기전용 백업 롤
                         ┌───────────────▼─────────────────────┐
   국내 백업 러너         │  국내 IDC/클라우드 VM (cron/pg_cron)  │
   (국내에서 처리)        │   pg_dump → 압축 → AES-256 암호화     │
                         │   → SHA-256 체크섬 → 매니페스트       │
                         └───────┬───────────────────┬─────────┘
                                 │                   │
              Tier1 (온라인)     ▼                   ▼   Tier2 (콜드/WORM)
         ┌──────────────────────────┐   ┌──────────────────────────────┐
         │ 국내 Object Storage       │   │ 국내 Object Storage (Object   │
         │ (일/주/월, 버전관리)      │   │  Lock) — 연 단위, 10년+ 보존  │
         └──────────────────────────┘   └──────────────────────────────┘
```

- **Tier 0 — Supabase 관리형 PITR**: WAL 기반 연속 백업. 임의 시점(초 단위) 복구. 오삭제·오갱신 사고의 1차 방어선.
- **Tier 1 — 국내 온라인 오프사이트**: 매일 논리 덤프(`pg_dump`)를 국내 Object Storage에 이중 보관. Supabase 계정/리전 상실에도 독립 복구 가능. 버전관리 활성화.
- **Tier 2 — 국내 콜드 아카이브(WORM)**: 월/연 단위 스냅샷을 Object Lock으로 **10년+ 보존**(의료법 §22). 보존기간 내 삭제·변조 불가.

> 국외이전 유의: Supabase Cloud 리전은 국외일 수 있음 → 개인정보 국외이전 고지·동의 및 리전 선택 검토. **엄격한 국내 저장이 필수라면 self-hosted(온프레미스)로 전환**하고 동일 파이프라인을 적용한다.

## 4. 복구 목표 (RPO/RTO)

| 계층 | RPO(최대 데이터 손실) | RTO(복구 소요) | 용도 |
|------|----------------------|----------------|------|
| Tier 0 PITR | **≤ 5분** (WAL) | ≤ 1시간 | 오삭제/오갱신 즉시 되돌리기 |
| Tier 1 일일 오프사이트 | **≤ 24시간** | ≤ 4시간 | 프로젝트/리전 상실 복구 |
| Tier 2 콜드 아카이브 | 월/연 | ≤ 24시간 | 장기보존·법적 제출·감사 |

## 5. 백업 파이프라인 (매일)

1. **스케줄** — 국내 러너의 cron(예: 매일 03:00 KST). 진료 트래픽이 낮은 시간대.
2. **덤프** — 전용 **읽기 전용 롤**로 `pg_dump -Fc`(custom format, 병렬). 스키마+데이터.
3. **압축** — 덤프 포맷 내 압축(zstd/gzip).
4. **암호화** — 랜덤 데이터키로 **AES-256** 암호화 → 데이터키는 **국내 KMS 마스터키**로 봉투암호화(파일에 미포함).
5. **무결성** — 산출물 **SHA-256** 체크섬 + 매니페스트(JSON: 시각·크기·체크섬·행수 스냅샷).
6. **업로드** — 국내 Object Storage(S3 호환)로 전송. Tier1 버전관리 / Tier2 Object Lock.
7. **기록·알림** — `backup_runs` 테이블에 결과 기록. 실패 시 즉시 알림(Slack/이메일/OneSignal).

> Tier 0(PITR)는 Supabase가 자동 수행하므로 별도 파이프라인 불필요. Tier 1/2만 러너가 담당.

## 6. 암호화·키 관리

- **알고리즘**: 저장 AES-256(봉투암호화), 전송 TLS 1.2+.
- **봉투암호화**: 백업마다 랜덤 데이터키(DEK) → DEK는 국내 KMS의 마스터키(KEK)로 암호화해 매니페스트에 동봉. 평문 DEK는 러너 메모리에만 존재.
- **키 분리**: 백업 사본과 KEK는 **서로 다른 계정/권한**에 저장. 백업 접근자가 단독으로 복호화 불가.
- **DB 내 민감정보**: 환자 이름·주민번호는 이미 pgcrypto AES-256로 암호화 저장 → 덤프에도 **암호문**으로 포함(이중 보호).
- **키 회전**: KEK 연 1회 이상 회전. 회전 시 기존 아카이브는 재암호화 없이 이전 KEK로 복호 가능하도록 KMS 버전 유지.

## 7. 보관 주기·파기 (티어별)

| 티어 | 주기 | 보존 | 저장소 | 비고 |
|------|------|------|--------|------|
| PITR | 연속 | 7~30일 | Supabase | 시점 복구 |
| 일일 | 1일 | 30일 | 국내 Object Storage(버전관리) | Tier1 |
| 주간 | 주 | 12주 | 국내 Object Storage | Tier1 |
| 월간 | 월 | 12개월 | 국내 Object Storage | Tier1→2 |
| 연간 | 연 | **10년+** | 국내 Object Storage(**Object Lock**) | Tier2, 의료법 §22 |

- **파기(secure deletion)**: 법정 보존기간(진료기록 10년) 경과분만 **거버넌스 승인 후** 파기. 파기 이력은 감사기록으로 남김. Object Lock 보존기간 이전 삭제 불가.
- 처방전은 §22상 2년이나, 운영 단순화를 위해 진료기록과 함께 10년 보존.

## 8. 무결성·복구 검증

- **체크섬 검증**: 업로드 직후·복원 직전 SHA-256 재계산 비교.
- **주간 복구 테스트(자동)**: 최신 Tier1 백업을 **격리 스테이징 DB**로 복원 후 검증 쿼리 실행 →
  - 핵심 테이블 행수·`max(updated_at)`가 매니페스트 스냅샷과 일치
  - 참조 무결성(FK) 오류 0
  - 보존 무결성: `chart_records`·`patients`에 물리삭제 흔적 없음(§22)
  - 감사로그 연속성(`audit_log` 최신 시각) 확인
- **결과 기록**: `backup_runs.verified` 갱신. 테스트 실패 시 알림 + 원인 분석.
- 스크립트: `ops/backup/restore_verify.sh`.

## 9. 재해복구(DR) 시나리오·런북

| 시나리오 | 1차 대응 | 절차 |
|----------|----------|------|
| 오삭제/오갱신(단일 레코드·테이블) | **PITR** | 사고 직전 시점으로 스테이징 복원 → 해당 레코드만 추출·병합 |
| 대량 손상/드롭 | PITR 또는 Tier1 | 사고 직전 PITR 복원. 불가 시 최신 Tier1 덤프 복원 |
| 프로젝트/계정 상실 | **Tier1 오프사이트** | 신규 Supabase(또는 self-hosted)에 덤프 복원 → 앱 연결 문자열 교체 |
| 리전 장애 | Tier1 | 대체 리전/온프레미스에 복원 |
| 랜섬웨어·백업 변조 | **Tier2 WORM** | Object Lock 불변 사본에서 복원 |
| 장기보존 제출(감사·소송) | Tier2 | 연 아카이브 복호화 후 read-only 복원 |

- **RTO/역할·연락체계** 문서화, **분기 1회 DR 훈련** 실시 후 런북 갱신.

## 10. 모니터링·거버넌스

- **대시보드**: 최근 성공 시각·크기 추세·복구테스트 상태.
- **알림**: 백업 실패·체크섬 불일치·복구테스트 실패·업로드 지연 시 즉시.
- **거버넌스**: 개인정보 보호책임자(CPO)가 백업/파기 정책 승인·감독. 백업 접근은 전원 감사기록.
- **접근통제**: 백업 롤은 읽기 전용, 복원 권한은 별도 승인. `backup_runs`는 superadmin만 열람.

## 11. 법령 준수 매핑

| 요구 | 근거 | 설계 반영 |
|------|------|-----------|
| 진료기록 10년 보존 | 의료법 §22 | Tier2 연 아카이브 10년+ · Object Lock |
| 물리삭제 금지 | 의료법 §22 | 백업 불변성(WORM) · 파기는 보존기간 경과분만 승인 후 |
| 접근기록·위변조 방지 | 의료법 §23 | `audit_log` 백업 포함 · 백업 접근 감사 · WORM |
| 개인정보 암호화 | 개인정보보호법 | 저장 AES-256(봉투) + DB 내 pgcrypto + 전송 TLS |
| 국내 보관 | 개인정보보호법 | 오프사이트 사본·처리 국내 수행 (국외이전 시 고지·동의 검토) |
| 정기 백업·안전조치 | 안전성확보조치 기준 | 매일 백업 + 주간 복구검증 + 최소권한·키분리 |

## 12. 운영 산출물

- `ops/backup/pg_backup.sh` — 일일 논리 백업(덤프→AES-256 암호화→체크섬→국내 업로드)
- `ops/backup/restore_verify.sh` — 격리 복원 + 검증 쿼리 + 결과 기록
- `ops/backup/backup.env.example` — 러너 환경변수 템플릿(비밀은 별도 금고)
- `supabase/06_backup_audit.sql` — `backup_runs`(백업 이력·WORM) + 무결성 스냅샷 함수

## 13. 향후 확장 (현재 범위 외)

- **Storage 버킷**(채팅 첨부·자료실·처방 스캔) 백업 — 동일 티어링 적용.
- **인증/설정/시크릿**(auth.users, RLS, Edge Function, 환경변수) 백업 — 금고 이중화.
- **교차 프로젝트**: PTCommunication·StaffCommunication·PsyTalk DB에 동일 파이프라인 적용(임상 DB가 최고 보존등급).
